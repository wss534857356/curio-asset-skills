# 宝石透射、陈列烘焙与拿放性能

在处理“像塑料／不透背景／拿起变色／第一次卡住／陈列太贵”时读取。先定位当前项目的材质、背景采样、灯光与资源归属，再选择所需分支。

## 把效果分开定位

| 现象 | 优先对照 |
| --- | --- |
| 面太少、折面不连续 | 灰模、线框、真实剪影与逐面法线 |
| 宝石像有一层金属纸封住 | 关闭可疑内部壳，改变后方实物颜色并翻看背面 |
| 一片白、像塑料 | 烘焙图是否又进入漫反射，是否叠加清漆或重复调色 |
| 拿起时突然换色 | 单位／缩放、吸收距离、远近材质的混合位置 |
| 第一次拿起卡顿 | 区分下载、解码、上传、着色器编译和首次离屏采集 |
| 多颗静态陈列仍昂贵 | 透射缓冲尺寸、同时启用的透射物件数量、反射采集频率 |

## 通透不等于降低 Alpha

以 MeshPhysicalMaterial 为例，使用透射时保持 opacity 为 1，结合厚度与吸收表达内部颜色。厚度、吸收距离和模型缩放必须使用一致的单位；只用一个缩放系数时，应明确均匀缩放前提。API 的参数范围与含义按目标 Three.js 版本核对，见 [材质文档](https://threejs.org/docs/pages/MeshPhysicalMaterial.html)。

游戏彩晶示例中的 IOR 1.55、云纹强度和吸收颜色是美术参数，不能直接称作真实钻石物性。目标是清澈钻石时，先确认参考、引擎支持的参数范围和所需光学等级；不要默认给它加入彩晶云絮。需要多次内部反射、全反射或可解释的色散时，另外评估能够实现这些行为的渲染方案与预算。屏幕空间透射、环境反射、镜头辉光和程序密度纹理各有边界。

没有实体背箔的设计，不应塞入一层不透明 BackSide 金属网格来假装亭部反光。这类网格可能先进入不透明背景缓冲，堵住外层要采样的真实背景。根据实际渲染器采用可用的前后表面体积方案，并检查它确实能看见后方物件。剧情中的真实背箔仍是独立部件，不能为了通透效果擅自删除。

## 用受控画面确认透射

保持模型、相机、灯光、曝光和反射环境不变，只把后方平面由红色改成蓝色，并放一条白色标记：

- 正面与背面都应响应后方实物的变化；切面可能使白条偏折。
- 颜色吸收会改变透过来的颜色，不要求结果等于背景原色。
- 对比同一取样区域或差异图，避免只凭“有亮点”认定透明。
- 分别改变反射环境与后景，确认反射和透射不是同一个静态替代图。

该对照用于诊断，不是珠宝真实性鉴定或完整光线追踪认证。

## 让陈列承担更低的成本

静态陈列可以保留真实闭合切型，使用低成本材质；只有当前拿近的一枚启用昂贵透射。网格本来已经很轻时，优先优化像素与离屏通道，而非继续减面。

若将近景效果烘焙供远观使用：

- 明确图中保存的是底色，还是已经受光的辐射结果。后者不要再当 albedo 叠一次漫反射、清漆和同一套高光。
- 在正确的线性／sRGB 链路中存取，避免烘焙时和显示时重复套用同一 tone mapping。
- 正反面可以共享一张图的分区，但需要独立映射、正确翻向与轮廓外扩色，避免腰棱采到黑边。保留原光学 UV；按引擎约定另用一个 UV 通道。
- 拿起／放回时在已受光结果与近景光学结果之间过渡；若把烘焙图混回漫反射底色，过渡中又会出现塑料感。
- 这种贴图固定了部分视角与光照结果，不能声称其内部层次是实时多次折射。

PNG/WebP 的下载大小不等于显存。单独估算解码尺寸、格式、mip、实例共享及离屏目标；整机 GPU 读数也不能冒充某一件宝石的独占开销。

## 稳定反射、透射预算和首用

- 房间环境采集由场景持有，宝石只借用。采集时排除所有使用该环境纹理的物件，避免自反馈；无论成功或失败，都恢复可见性、阴影状态与渲染目标。
- 房间／光照真正变化后刷新环境。仅旋转、放大、拿起或放回时复用缓存。
- 限制近景透射目标的长边，并与主画面分辨率、DPR 分开。项目的桌面 512／窄屏 384 像素是起始案例，不是适用于所有游戏的上限。
- 首次拿起前异步准备实际会用到的程序变体。Three 0.185.1 的案例中，DoubleSide 透射实际还会走 BackSide 通道，只预编译表面声明的版本仍会留下首次卡顿。其他版本应重新检查实际渲染路径。
- 复用既有灯光，避免在第一次操作时临时增加灯光种类或数量。不要为每枚宝石各建一套重复灯光和环境图。
- 明确共享几何、贴图和环境的所有者。替换临时材质时恢复原材质与回调；借用的环境纹理不由单颗宝石释放。

验证首次操作、重复拿放、连续切换、取消拿起、正背面和最大检视缩放。分别记录编译、离屏采集和资源计数；渲染优化完成不等于页面所有长任务都消失。按改动风险选择检查，不为纯文档更新重跑整个游戏。
