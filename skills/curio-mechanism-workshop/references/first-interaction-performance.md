# 首次交互卡顿：定位、修复与验证

适用于点火、开灯、切材质、打开机关等动作第一次明显停顿、再次操作顺畅的情况，以及新增会改变灯光／材质配置的交互。先确认实际耗时来源；静态资产或文档修改不自动触发整场景性能审计。

## 先判断是一次性准备，还是持续渲染成本

在相同机位、分辨率、浏览器和 GPU 后端下比较：新页面首次操作、复位、第二次操作。等待资产进入可操作状态，再开始计时；分别记录加载期间和点击期间的工作。隔离测试存档，不用清空玩家进度制造“冷启动”。

| 证据 | 优先检查 | 对应处理 |
|---|---|---|
| 首次新增 shader/program，后续命中缓存 | 灯光数量、材质 defines、贴图有无、透明／透射／阴影配置 | 稳定配置，或在加载阶段准备必要的实际变体 |
| 没有新程序，但首次有下载、解码或上传 | 图片解码、纹理 GPU 上传、模型解析 | 按需要提前加载／解码／初始化，保留加载反馈 |
| 首次出现渲染目标或阴影资源分配 | 阴影、反射、后处理缓冲及尺寸 | 提前准备必要资源，复用项目更新与缓存策略 |
| 主线程集中创建对象、几何、音频或做计算 | 点击回调中的构造、同步工作、GC | 复用实例；将必要的一次性准备放入合适的加载阶段 |
| 每次操作或持续燃烧都慢 | 常态 GPU/CPU 成本、阴影更新、重复 RAF、绘制调用 | 分析持续成本，再调整几何、材质或更新频率 |

“第二次不卡”只是一条线索。网络请求完成也不代表 GPU 资源已经准备好。不要用统一降画质或减面代替定位。

## 本例：守夜鸦提灯为什么第一次点火卡住

本例基于 Three.js 0.185.1 的 WebGLRenderer。火焰组里同时放了两层火焰网格和一个 PointLight，原来的开关是：

```ts
fire.visible = heat > 0.005;
```

关闭父组会让它的子点光源退出渲染器的可见灯光列表。第一次点火重新加入这盏灯，场景的灯光数量发生变化，一批受光材质需要新的着色器程序。第二次点火使用已缓存的组合，因此变得顺畅。

2026-09-26 在独立 Chromium / ANGLE D3D11 页面，用真实开门与灯芯点击核对：

| 点击阶段 | 修复前 compileShader / linkProgram | 修复后 compileShader / linkProgram |
|---|---:|---:|
| 第一次点火 | 28 / 14 | 0 / 0 |
| 熄灭 | 0 / 0 | 0 / 0 |
| 再次点火 | 0 / 0 | 0 / 0 |

28 次 shader 编译对应本例 14 个程序的顶点／片元阶段，不是 28 件模型。修复后首次点火的本机采样最大 RAF 间隔约 16.8 ms；这不是所有设备的帧率承诺。

## 修复：保持渲染配置稳定，只改变显示与亮度

本例的火焰是很小的、无骨骼的发光网格，点光源不投影。让它们在物件初次显示时进入准备过程，熄灭时使用零缩放和零强度；点火时复用同一组对象、材质和灯光。

```ts
// 创建时：fire 含已有火焰网格与 glow 点光源。
const authoredScale = fire.scale.clone();
fire.visible = true;
fire.scale.setScalar(0);
glow.intensity = 0;

// 动画时：heat 和 pulse 仍由现有点火/熄灭过程驱动。
const burning = heat > 0.005;
fire.scale.copy(authoredScale).multiplyScalar(burning ? 1 : 0);
glow.intensity = burning ? peakIntensity * heat * pulse : 0;
```

- 熄灭阈值以下明确将强度置零。阻尼可能永远不精确到零，按需渲染的页面又会停止更新；只缩掉火焰、留下很小的正强度会产生残光。
- 灯芯点击目标保持独立，不随火焰缩掉。保留“先开门才能点火”、关门后继续燃烧及再次熄灭的原规则。
- 核对火焰确实在初始准备范围内：父级隐藏、相机裁剪或未加载仍可能阻止预期的首次绘制。以编译计数和冷启动操作证明效果。
- 零缩放会产生不可逆变换。需要矩阵求逆、骨骼、碰撞或复杂挂点的对象，不直接套用此例；可把灯光与显示网格分开管理，并准备实际需要的材质变体。
- 只给当前加载、即将交互的少量物件保留必要配置。零强度灯光仍有渲染管理成本，不把库存里所有提灯都变成常驻实时灯光。
- 准备成本并没有凭空消失：它应发生在合适的加载阶段，并继续检查该阶段是否产生新的明显停顿。

这不是“禁止使用 visible”的通用规则。整件藏品卸载、远处物件裁剪仍按项目原有策略处理；需要避免的是在高频交互开关中意外改变整场景的着色器组合。

## 需要预编译或预上传时

先读目标项目已安装版本的渲染器实现和接口。Three.js 的 `compileAsync(scene, camera, targetScene?)` 可准备材质程序，并利用 `KHR_parallel_shader_compile`；调用前配置真实的灯光和环境，覆盖需要的开启状态。只在灭灯配置下编译，不代表点灯后的组合已经准备好。[WebGLRenderer 文档](https://threejs.org/docs/pages/WebGLRenderer.html)

编译着色器与纹理上传、渲染目标分配分开核对。根据目标版本与实际瓶颈使用 `initTexture`、`initRenderTarget` 或项目现有加载接口；不要把一次 `compileAsync` 返回当成所有资源的首用成本都已消除。

优先在运行中改变亮度、颜色等 uniform 值。贴图从无到有、材质结构或 defines 变化等可能需要新程序，应按实际配置准备；仅因动画推进，不每帧设置 `material.needsUpdate`。[材质更新说明](https://threejs.org/manual/pages/how-to-update-things.html)

## 验证首次操作，而不是只验证热缓存

1. **冷页面复测。** 固定目标物、机位、曝光和渲染后端，完成首次开门／点火、熄灭和再次操作。另看静止、燃烧中和熄灭后的常态表现。
2. **计数与耗时分开。** 可读取 `renderer.info.programs`，或在隔离调试页面临时统计 `compileShader` / `linkProgram`。程序增量能指示新组合，不能单独代表 GPU 总耗时；结合帧间隔、Performance 时间线和必要的 GPU 工具。
3. **覆盖延迟帧。** 在点击前开始采样，结束前再等待至少两个 RAF。固定计时窗口可能恰好在长停顿返回之前结束，使记录中的最大帧间隔看起来正常。本例旧探针就漏掉了该延迟帧，不能据其最大帧间隔计算性能提升百分比。
4. **检查真实渲染状态。** 保证未点燃时没有火焰残片和残光；点燃后外观、亮度、位置正常；点击区域仍有效；关闭再打开、销毁重建和按需渲染都保持原行为。只测实际受影响的入口与状态。
5. **留下能抓住根因的回归。** 本例验证可见灯光集合在点火前后不变、两层火焰材质复用、熄灭无可见几何和残余强度，以及原有开门限制。单元测试不能证明 GPU 帧耗时，仍需实际浏览器证据。

记录版本、GPU 后端、首次／重复操作的新程序数量与检查范围。区分“消除了点击期间的新编译”“稳定帧率达到多少”和“尚未测过的设备”，不要只交付一张点着的截图。
